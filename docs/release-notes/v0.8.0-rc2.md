# 0.8.0-rc2 — retained layout and dependable verification

Release candidate with **RimWorld 1.6 and basic 1.7 compatibility**, not a stable/latest release.
Native 1.7 rendering and main interactions still await human acceptance. FerriteLib remains a no-content
prerequisite with one runtime DLL, no Defs/patches/textures and no settings or save data of its own.

## Changes from rc1

- Read-only bindings on `text/wrapped` now use normal foreground rather than disabled grey, subject
  to Tone/Emphasis/TextColor. This is the shared FL baseline: A and B both become brighter, as does
  delivery-r8 when it adopts the new FL, even where A's own source is unchanged. Interactive read-only
  controls and explicit shared writable:false calls retain their previous behavior.
- Seven optional TextColor slots inherit independently without adding palette roles. Theme/instance/local
  runtime declarations use the public-unstable UiTextColours facade; resolved styles carry the selected ink.
- Native event mapping uses explicit enum values; Repeat template-root visibility follows the normal
  invalidation path.
- Canonical palette lookup avoids repeated parsing/reflection. Resolved appearance and detached rollback
  facts are reused only while their actual declaration, ancestor, theme and font inputs remain valid.
- The shared synchronous layout pipeline validates stable domains before full candidate preparation.
  It uses first-write leaf records, first-touch arrangement backups and immutable sparse geometry.
  Unknown/legacy/structural domains retain the complete transaction, including multi-root remaining-height
  dependencies. Draw, current hit geometry, native editors and required Repaint calls remain active.
- Verification now restores explicit roots once, builds distinct Core/Release/Dev variants and executes
  the built outputs. Stub dependencies share the normal graph. Complete logs and input/configuration,
  exit and timing summaries survive failures as well as success.
- A local basic 1.7 compatibility candidate isolates Unity-only font-environment metadata from the
  common text path. Unity 1.6 retains its original fingerprint; other font providers use the existing
  conservative no-reuse contract. Both game versions select one payload. Native 1.7 rendering and
  main interactions remain awaiting human acceptance; this is not a complete Waylith adapter.
- Standard draw guards retain and report request errors and their actual target without tripping the
  widget, retrying the request or rolling back business effects. Optional reporting failures stay isolated.
- A registry first explicitly enrolled after Host construction joins that view's presentation and
  demand pipeline at the next legal synchronization; ordinary bindings need no early registration.
- Initial document attachment restores staged Host state on failure and changes dependencies only
  after staging succeeds. Seal/retirement remains an irreversible committed result.

## Compatibility and upgrade

Supported 0.8 source, compiled-consumer, XML and legal-use contracts remain protected. There is no new
purity/subscription prerequisite for ordinary getters, old Measure or ITextMetrics. The API/build base
remains 0.8.0; the rc2 tag/archive identifies the trial, while the DLL additionally records its real source
commit. Retained domains still perform validity/Draw/hit walks; this is not pixel retention or automatic
background layout.

Exit the game before replacing the complete FerriteLib folder with the selected package. Keep exactly
one enabled carrier of FerriteLib.UiKit.dll; do not put a second copy in a consumer mod. Consumers compile
against that exact fixed DLL with Private=false and assert their supported API range, normally
[0.8.0,0.9.0). Keep the last accepted complete consumer/library pair for rollback. Do not clear player
configuration to upgrade the library, and do not disable it while an enabled consumer depends on it.

Use the DLL from the selected release asset. Its tag and full source commit identify the package;
local development builds have separate identities.

## Playtest results and known limitations

Numeric FontSize1..96 is implemented in the current source through public-unstable composed production
entries, without changing Stable signatures or old singleton/override conditions. Standard windows and
independent authors can use the same effective alias/size for measurement, layout, drawing, cache, fit
and retained display. Explicit text/state colour reaches the real native editor request, not only labels.
Invalid numbers are refused; unsupported purposes report the effective preset and reason.

The1.6 numeric label/editor routes remain **静态候选、待原生**.1.7 labels are a source-level candidate
with an explicit capability switch; editors do not support numeric size and fall back with a report.
No1.7 numeric-label level is advertised for release before the user's1.7 screenshot coverage. Font/IME,
caret/selection, exception-state restoration, language fallback, UIScale and extreme-size behavior remain
native acceptance gaps. Existing stub checks are not pixel acceptance. See the
[implementation status](../openspec/implementation.md#appearance-freedom) and
[author guide](../consumers/consume-from-0.8.0-dev.md#choose-one-effective-font-for-measurement-and-drawing).

The user accepted stable FPS for US2f22bec/FL833c14f4 and later reported that
USea610fa/FL833c14f4 worked well in internal playtesting. The trial did not include a detailed
per-action, resolution, language or IME record.

Cold-opening peaks, independent HUD cost, detailed font/IME/overlap/scaling and real configuration-save
coverage remain incompletely characterized. Some earlier headless game checks reported errors.
The local basic 1.7 candidate is described in the [build guide](../build-and-debug.md#basic-17-compatibility-candidate).
No complete/native-accepted 1.7 adapter, new window manager or asynchronous dispatch is delivered.
