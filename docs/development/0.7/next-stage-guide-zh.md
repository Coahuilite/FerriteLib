# FL 0.7.x 下一阶段开发手册

这份手册说明接下来开发什么、为什么先做，以及完成的标准。构建、选取 DLL、读取诊断的具体命令见
[构建与调试操作说明](../../build-and-debug.md)；开放任务统一维护在 [TODO.md](../../../TODO.md)。

## 目标与已经确定的边界

维护者在 2026-09-24 确认：优先建立稳定、可扩展、可由多个模组共用的 FL，接受 US 继续延期；使用 US
ModSettings 的既有 UI 重构计划作为实际推进面。沿用 retained page model + Verse IMGUI，逐个完善契约。

US 的计划负责定义真实页面需求，FL 负责判断其中哪些属于通用库职责。FL 自身构建、测试和打包仍须独立，
不能要求所有库开发者拥有 US 仓库。现行 API 分层、迁移规则和 0.7.x 临时版本豁免继续遵循 `AGENTS.md`。

**本阶段的边界（2026-09-24 口径；完整裁定、日期与到期条件见团队台账与各仓 `MEMORY.md`，本手册不复制裁定清单）：**
FL 停在 `0.7.x` 开发状态——不抬 minor、不进入下一条线，临时豁免继续有效，到期 = 首发/tag 或锁步结束；
远端只作异地备份，不打 tag、不做 release；本地测试只用 Dev 包（`pack-release` / `pack-steam` 本阶段不跑）；
金色身份采用系列金 `UiTheme.DarkGold` / `AccentGold`，外部外观基准的 `#EBAD4D` 不采用。

| 归属 | 内容 |
| --- | --- |
| FL | 元素身份、测量与布局规则、坐标转换、输入与弹窗仲裁、状态和订阅生命周期、恢复、诊断事实 |
| US | 游戏业务数据、设置含义、命令行为、页面组合、产品文案和具体视觉选择 |
| 需要逐项判断 | 新控件、样式词汇和绑定能力：说明现有组合方式为何不足，再决定通用能力的最小形状 |

多模组共用要求重点审查宿主隔离、状态释放、兼容性和清晰的输入输出契约。第二个模组的接入能够增加证据，
现有契约的稳定工作可以独立推进；不能把“已经可共用”写成“已经在多个模组中验证”。

## 起点：已经做了什么，还缺什么

构建已分到 `dist/build/Dev`、`dist/build/Release`，现有打包脚本继续生成 `dist/dev` 等目录。兼容路径的 DLL
只有显式导出才更新。US 能明确选择 FL DLL，编译记录与打包检查使用同一个哈希，避免验证和安装的输入错配。

FL 的开发诊断已记录布局数值、坐标空间、事件进入 Host 时的类型、按钮查询前后的事件类型。数据有界、按宿主
隔离、默认关闭，不能反过来决定布局或输入。消费前后记录、测试替身的事件与裁剪语义已有自动化检查；证据范围
和故意回退验证见操作说明。

**US Packs 行点击失效的根因尚未确认，真实游戏 E2E 尚未通过。** 自动化检查通过只支持已检查的契约。
这些准备工作不构成 FL 整体架构已经稳定的结论。

## 推进顺序

### 1. 关闭一个真实交互问题

使用哈希匹配的 FL/US Dev 包，在 RimWorld 中复现 Packs 行点击失效，同时保留可工作的筛选按钮作为对照。
记录窗口尺寸、UI 缩放、语言、滚动位置、目标行、期望与实际选择，以及对应的诊断记录。

沿着“可见区域与坐标 → 命中查询 → 事件是否已被消费 → 命令是否到达 → 状态是否刷新”定位。当前日志不能回答
某一步时，补这一处观测点；例如裁剪链、阻挡元素或命令到达记录，都需要具体缺口支撑。已有 `covered` 分支缺少
直接测试，可以作为独立的库内补证任务，但不能代替游戏复现。

先决定缺陷属于 FL 还是 US，再做最小修复。完成标准：原始问题在游戏中通过，重复同位置点击、滚动后点击、
弹窗遮挡等相邻场景未回归；能在自动化中表达的失败条件有对应回归检查。无法复现时保留条件与未知项，避免猜测性修复。

### 2. 随 US 页面切片完善通用契约

继续使用 US 已有重构计划，每次选一个可交付的页面切片，完成需求、库边界判断、实现和验收。根据这个切片实际
触及的能力检查以下契约，而不是一次重写所有层：

| 契约 | 必须能回答的问题 |
| --- | --- |
| 测量与布局 | 给定宽度和约束，高度如何产生？最终分配空间与绘制空间是否一致？ |
| 坐标与裁剪 | 指针、布局、绘制分别在哪个空间？滚动和裁剪如何影响可交互范围？ |
| 输入与命令 | 禁用、消费、弹窗覆盖如何影响事件？一次操作触发几次业务命令？ |
| 状态与生命周期 | 身份如何稳定？模型变化何时失效？关闭、重开及重载后谁释放订阅？ |
| 样式 | 哪些值只影响绘制，哪些会改变测量？默认值、覆盖与回退由谁负责？ |
| 诊断 | 数值从哪个真实边界采集？关闭是否避免采样成本？遗漏和未知是否明确报告？ |

边框/单边宽度（task-11）等已提出能力保留在候选队列；由当前页面切片确定其优先级。层级行模板 FL-17 等
已有条件或延期的项目保持原条件，不因本手册自动获准实现。

### 3. 把验证过的能力整理为可依赖的库表面

为准备稳定的能力写清楚合法输入、状态所有权、布局与输入行为、错误和回退方式、兼容承诺，以及消费者示例。
按 `docs/api-tiers.md` 逐项决定层级，保留迁移路径。单个页面通过不能自动把所有公开成员提升为 stable。

这批条目的书写模板（八栏，含「证据与缺口」）与首批三个试写样例（裸命中带 `Chrome="none"`+`Height="MatchContent"`、
`PayloadKey`、`SelectedKey`，各带消费者引证与 UNRUN 标注）在 [0.7 契约文件](05-api-contract.md) 的
"Dependable-surface entries (stage 3)" 一节。**模板只是书写形式，不代替逐项分层决定**；`docs/api-tiers.md`
里两条理由的复核见 [60-capability-dispositions.md](60-capability-dispositions.md) §C——**一条理由已失效（`LineChartWidget`）、一条引证过时但结论仍成立（`UiChartPointChange` 仍被消费者源码按类型命名）**。

对多宿主共用有直接影响的共享状态应单独审查，例如 `UiFitAudit.Enabled` 的全局开关；目前它是已知风险，
不能写成已经复现的跨模组故障。新增通用控件和大型可视化检查器仍需具体用途支撑。

## 每个切片如何验收与交接

分别报告三个结果：自动化契约检查、构建/安装输入身份核对、真实游戏 E2E。涉及真实交互或几何的缺陷，在对应
游戏验收完成前保持开放。对纯文档、构建工具等改动，则按自身风险验证，不虚构它们需要游戏验收。

每个切片交接时留下：问题与复现条件、归属判断、改动和契约影响、已执行的验证、仍未知的部分及下一步。
`MEMORY.md` 只保留长期事实和证据入口，`TODO.md` 只保留当前行动，具体开发规则集中在本手册。一次代码或文档
提交不会自动更新既有安装包；测试结论必须指向实际测试的产物。
